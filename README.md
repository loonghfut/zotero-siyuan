# Zotero → SiYuan

[![CI](https://github.com/loonghfut/zotero-siyuan/actions/workflows/ci.yml/badge.svg)](https://github.com/loonghfut/zotero-siyuan/actions/workflows/ci.yml)
[![Release](https://github.com/loonghfut/zotero-siyuan/actions/workflows/release.yml/badge.svg)](https://github.com/loonghfut/zotero-siyuan/actions/workflows/release.yml)

把 Zotero PDF 阅读器侧边栏里的**注释（annotation）和它上面的评论（comment）**，一键写进
**思源笔记** —— 默认是**当天的日记**，也可以指定一篇文档，或者为每篇文献单独建一篇笔记。

在 Zotero 阅读器的左侧注释面板中，每条注释标题旁会出现一个 ➡ 按钮。点它之后：

- 注释选中的原文 → 思源的 `> [!quote]` 引用块
- 你自己写的评论 → 思源的 `> [!note]` 备注块
- 作者 / 年份 / 出处 / 页码 / 批注人 → 一行元信息
- 文献标题 → 一个 `zotero://open/library/items/…?annotation=…` 深链，点开直接跳回 Zotero 的**那条注释**

写完之后，注释旁边会多出一个 ↗ 标记，点它直接跳到思源里对应的那一块。

除了侧边栏那一个按钮，还有三条路：

- **批量**：选中多条注释右键，一次发完（只写一次，不是 N 个进程）；
- **自动发送**：打开一个开关后，新注释按颜色 / 标签 / 类型 / 文献分类自动发（默认关闭）；
- **条目列表**：不打开 PDF 也能右键发送文献信息、摘要、笔记、全部注释，或者直接建一篇文献笔记文档。

写入效果（思源日记里）：

```markdown
> [!quote] 摘录 · Attention Is All You Need
> The dominant sequence transduction models are based on complex recurrent or convolutional neural networks.

> [!note] 批注
> This is the core idea of the paper.

作者：Ashish Vaswani  
年份：2017  
出处：Advances in Neural Information Processing Systems  
页码：3  
批注人：steve  
来源：[Attention Is All You Need](zotero://open/library/items/ATTACH01?annotation=ANNO0001&page=3)
```

## 写到哪儿

设置面板的「发送到」一节决定笔记的去处：

| 目标 | 说明 |
|---|---|
| **今天的日记** | 默认。和思源自己的「设置 → 外观 → 日记」保持一致，不用填路径 |
| **指定文档** | 填文档标题或块 ID。标题会按工作空间里的最新一篇查找，找不到会直接说，不会悄悄写到日记里 |
| **每篇文献一个文档** | 在所选笔记本里为这篇文献建一篇文档，标题可以用模板变量（默认 `{{title}}`），并放在指定路径下。文档第一次建好后会打上 `custom-zotero-item-key` 属性，以后这条文献的注释都写进同一篇 |

「每篇文献一个文档」不会在 Zotero 库里留任何标记：它靠思源文档自己的自定义属性找回那篇文档，
换一台机器、换一个 Zotero 库都能接着用。

这个目标可以**单独用一份模板**：在「发送模板」顶部把「模板用途」切到「每篇文献一个文档」，
写文献笔记该有的样子；留空就沿用通用模板。批量发送到这种文档时，整批都用这份模板。

文献笔记的三个区段也各有模板：「文献信息」「摘要」「笔记（每条一次）」。留空时用内置写法
（一个 callout 加内容），改了就存成你自己的。区段模板多了几个变量：`{{metadataCallout}}`、
`{{abstractCallout}}`、`{{note}}`、`{{noteCallout}}`、`{{noteNumber}}`，以及三个标题
`{{itemInfoLabel}}` / `{{itemAbstractLabel}}` / `{{itemNotesLabel}}`。

模板里**记得写上正文变量**（笔记用 `{{noteCallout}}`，摘要用 `{{abstractCallout}}`，
信息用 `{{metadataCallout}}`）。只写标题不会自动补正文——但编辑框下方会直接提示
“the body is missing — add {{noteCallout}}”，不会让你在思源里才发现内容没了。

**子笔记里的图片会一起发过去。** Zotero 把笔记里的图片存成这条笔记下的独立附件
（旧版笔记则写在 HTML 里），思源打不开那种地址；插件会把图片放进思源的 `assets/`
（和框选图片同一条压缩流程），再把笔记里的引用改过去。文件名按图片本身固定，
重复同步不会在 `assets/` 里堆副本；某张图找不到时只是少这张图，笔记照写。

## 已经发过的注释

发送前会先查索引。如果这条注释已经写进思源，会弹一个气泡让你选：

- **打开已有** —— 跳到上次写的那一块
- **仍然发送** —— 再写一条（旧的不动）
- **替换上次** —— 先写新的，成功后再删掉上次的块和它带进来的图片；新的一条没写成功时，旧的原样保留

不想每次都被问，可以在设置里把「已经发过的注释」改成**跳过**、**再发一条**或**替换上次**。
批量发送时不逐条提问：按这个偏好处理，「跳过」的条数会在最后的汇总里写出来。

## 自定义发送模板

设置面板里有一个模板编辑框，写的是**普通 Markdown**，用 `{{变量}}` 插入内容：

```markdown
> [!quote] 摘录 · {{title}}
{{imageCallout}}{{quoteCallout}}

{{#if comment}}> [!note] 批注
{{commentCallout}}

{{/if}}{{metadata}}
```

- `{{变量}}` —— 插入一个值
- `{{#if 变量}}…{{/if}}` —— 只在变量不为空时保留这一段（没有评论时就不会留下空的批注块）
  - 条件可以**嵌套**：`{{#if a}}{{#if b}}…{{/if}}{{/if}}`，`{{/if}}` 会和最外层的那个配对
- `{{else}}` —— 条件的**另一分支**：变量为空时走这一段
  - 嵌套时，`{{else}}` 归它**所在的那一层**条件 —— 内层的 `{{else}}` 不会抢外层的
  - 没被走的那一支会连它占的行一起消失，不会留下空行
- **没有值的变量不会留下空行**：一行里如果只有变量、而它们都没有值，这一行**整行消失**。
  行里如果有自己的文字，那一行保留 ——「作者：」还在，只是没有名字

  ```markdown
  {{quoteInline}}   ← 没有值，这一行消失
  {{image}}         ← 没有值，这一行也消失
  {{comment}}       ← 有值，从这里开始
  [{{title}}]({{zoteroAnnotationLink}})
  ```

  → 写出来是

  ```markdown
  你的评论
  [论文标题](zotero://open/library/items/…)
  ```

- 面板下方有**实时预览**，用的是你库里真实的一条注释，边写边看效果
- 还有一张**变量速查表**，列出所有可用变量和它们的含义
- **点一下变量名，就把它插到模板的光标处**；模板里已经用过的变量会加粗，变量按用途分组。
  插好后光标停在插进去的内容后面，所以可以连续点好几个变量

### 编辑模板时少走弯路

写模板最费劲的是「不知道从哪开始」和「变量太多找不到」。面板为此做了几件事：

| | |
|---|---|
| **模板预设** | 顶部有下拉框：默认、极简、框选图片单独一行、全文笔记。挑一个，再改细节 |
| **语法校验** | 编辑器上方会直接说「哪个变量不存在」「哪个条件没闭合」「哪个 `{{else}}` 没有对应的 `{{#if}}`」—— 不用等发出去才发现 |
| **变量过滤** | 变量表上面有搜索框，按**名字或说明**过滤；还有个「只看已用」开关 |
| **Tab 缩进** | 编辑框里按 Tab 插入两个空格，而不是跳到下一个控件 |
| **整块变量独占一行** | `{{quoteCallout}}` 这类变量自带 `> `，插到行中间会把引用块弄坏 —— 插件会自动换行，并**保留那一行的缩进** |
| **条件块可视化插入** | 条件不用手敲：选好变量，点「插入条件块」，选中的一段就被**包进** `{{#if 变量}}…{{/if}}` 里；没选中就插一个空块，光标停在两个标签之间。「插入 else」「插入结尾」两个按钮补上另外两端 |

### 保存你自己的模板

调好的模板可以存起来，随时换回来 —— 面板的「发送模板」一节里有一行**我的模板**：

| | |
|---|---|
| **保存** | 在名字框里起个名字，点「保存」，当前编辑框里的模板就存进去了。名字和已有的一份相同 → **更新那一份**，不会堆出重复 |
| **套用** | 在下拉列表里选中一份，点「套用」，它就回到编辑框里 —— 并立刻成为**正在用的**模板；如果它是在「每篇文献一个文档」那边保存的，编辑框也会切回去 |
| **删除** | 选中一份，点「删除」—— **要按两次**，第一次只是问一句「再按一次「删除」就会删掉 X」，因为这件事没有撤销 |
| **更新选中的那份** | 名字框**留空**、但列表里选中了一份时，点「保存」就是把编辑框里的内容存回**选中的那一份** |

- 模板存在 Zotero 的偏好里（`extensions.zotero.zoteroSiYuan.templates`），跟着 Zotero 走，不写在思源里
- **模板会连「发送到」一起存**：保存时把当前的目标位置、指定文档、每篇文献文档的标题和路径写进去，
  点「套用」时一并恢复 —— 所以「每篇文献一个文档」的用法可以只做一个模板
- **模板也记得自己属于哪一边**：在「每篇文献一个文档」的编辑框里保存的模板，套用时回到那一边，
  不会把文献笔记的写法塞进日记模板
- 最多 50 份；**空模板不存**，没名字也不存 —— 面板会直接说为什么没存上
- 列表里一份都没有时，「套用」和「删除」两个按钮是**灰的**，不是按下去没反应
- 偏好是可以手动编辑的：写坏了（不是合法 JSON、不是数组、缺字段）**面板照常打开**，最多读到一份空列表

条件块的几条规矩：

- 两个标签**各占一行**，中间的内容**原样保留**（不缩进、不改字）
- 标签跟着**插入位置那一行**的缩进走
- 后面同一行还有别的内容时，标签会**另起一行**，不跟别人挤在一起
- 按按钮时**选区不会丢** —— 光标和选中的范围都会记住，所以「先选中、再点按钮」真的能包住选中的那段

主要变量：

| 变量 | 含义 |
|---|---|
| `{{quote}}` `{{quoteCallout}}` `{{quoteInline}}` | 摘录原文：原样 / 每行加 `> ` / 转义成一行 |
| `{{comment}}` `{{commentCallout}}` `{{commentInline}}` | 你的批注，同样三种形态 |
| `{{image}}` `{{imageCallout}}` | 框选注释的截图（原样 / 每行加 `> `），普通注释为空 |
| `{{title}}` `{{titleInline}}` | 文献标题 |
| `{{authors}}` `{{author}}` `{{year}}` `{{publication}}` | 作者 / 第一作者 / 年份 / 出处 |
| `{{doi}}` `{{isbn}}` `{{url}}` `{{abstract}}` `{{itemType}}` `{{tags}}` | 其它文献字段 |
| `{{page}}` `{{pageNumber}}` `{{annotator}}` `{{annotationType}}` | 注释所在页 / 批注人 / 注释类型 |
| `{{annotatorDate}}` | 这条注释的最后修改时间（本地时钟，精确到分） |
| `{{date}}` `{{time}}` `{{timestamp}}` | 发送当天日期与时刻 |
| `{{zoteroLink}}` | 打开条目的 `zotero://` 链接 |
| `{{zoteroAnnotationLink}}` | **直接跳到这条注释**的 PDF 位置 |
| `{{metadata}}` | 作者/年份/出处/页码/批注人/来源，整块 |

## 框选注释（图片注释）

在 PDF 上**拖拽框选**一段区域，Zotero 记下来的是一条 **image / ink 注释**：它**没有文字**，
选中的内容是一张**截图**。这类注释以前发过去等于「发了个空引用块」，选区本身全丢了。

现在这类注释会把**图片一起送到思源**：

- 图片从 Zotero 的缓存里取（`<Zotero 数据目录>/cache/library/<注释 key>.png`），
  **压缩之后**放进思源工作空间的 `data/assets/` 下
- Markdown 写成思源自己的样子：`![框选](assets/zotero-siyuan-<注释key>-<时间戳>.jpg)`
- 图片放在 `> [!quote]` 引用块**里面** —— 框选的内容本身就是「摘录」，
  所以**默认模板不用改**就能正确输出
- 思源内核会**自己**把这份资源登记进它的资源表并生成真正的 `<img>`，
  插件不需要再上传一次

### 发送前先压缩

框选注释的图片是**页面截图**：它带着一条**其实全不透明**的透明通道，
所以每个像素要占四个字节 —— 一张 1918×819 的图能有 **975 KB**，
里面其实只是一页白底黑字。

插件在放进工作空间**之前**把它重新编码成 JPEG（透明处铺白底），
体积掉一大截。下面是**实测**的数字（同一张 1741×803 的框选截图，原始 2,262,931 字节）：

| 压缩质量 | 发出的大小 | 占原来的 |
|---|---|---|
| 30 | 136 KB | **6%** |
| 82（默认） | 348 KB | **15%** |
| 95 | 1,073 KB | **47%** |

设置面板的「**图片**」里可以（框选截图和子笔记里的图片共用这一套）：

- **关掉压缩** —— 想保留原始 PNG 就取消勾选
- **自己定压缩程度** —— **10～100 随便填**，也可以拖滑块：
  数字越小图越小也越糙，100 最大最清楚

三条规矩：

- **压完反而更大就保留原图** —— 已经是小图的图片不会因为压缩而变难看
- **压缩失败不算错误** —— 笔记照写，只是图片没压（没有画布的环境里就是这样）
- **JPEG 没有透明通道** —— 透明的地方铺成白色，和 PDF 页面的底色一致

> 自检里会写清楚这张图**压没压、压前多大、压后多大**。
> 压前的图超过 100 KB 却没压，会被当成**失败**报出来 —— 压缩坏了要有人知道。
>
> 自检报告里还有 `pluginVersion`：**跑的是哪一版代码**。
> 换 XPI 之后 Firefox 可能还会用一版旧代码再跑一次 —— 这个字段一眼就能看出来。

> **模板不用改也能有图。** 如果你的模板里没有 `{{image}}` 或 `{{imageCallout}}`，
> 插件会把图片**自动追加**到笔记末尾 —— 选区不该因为模板写得早而丢失。
> 反过来，模板里写了 `{{imageCallout}}` 的话，图片就放在你指定的那一行，
> **而且只出现一次**（`{{quoteCallout}}` 不会重复它）。
>
> 图片找不到时（缓存文件缺失、注释是同步过来的）**不会报错**：笔记照写，只是没有图片 ——
> 一张丢掉的图片不该连你的评论一起丢掉。
> 阅读器手里还带着这张图时，会退回用它的内存副本补上。
>
> 文件名里带时间戳，是为了每次发送都得到**独立的资源**，
> 免得同名文件在思源的资源表里变成重复行。
>
> 图片是在**笔记写入之前**放进工作区的 —— 笔记得指向一个真的存在的文件。
> 所以写失败的时候插件会**把自己那张图删掉**，自检也会把它写进去的图片**收回来**：
> 工作区是用户的，不留垃圾。

### 框选图片看得见吗？

设置面板里有一个「**检查框选图片**」按钮：它把库里所有框选注释列出来，
告诉你 Zotero 的缓存目录在哪、每条注释的图片路径算出来没有、**文件在不在磁盘上**。
图片发不出去的时候，先点这个 —— 断在哪一环，一眼就能看出来。

端到端自检里也有同样的一步：它拿一条**真实的**框选注释跑完整条链路
（找图 → 放进工作空间 → 渲染 → 笔记里有没有图片链接），结果写在自检报告里。

> **每一次图片发送都会留下"链路记录"**：是不是框选注释、key 是什么、
> 缓存路径算出来没有、文件在不在、工作空间是哪个、导出成功没有。
> 出问题的时候，报告里直接写着**卡在哪一环、报的是什么错** ——
> 一个什么都不说的失败，是最难找的那种失败。

## 双向跳转

| 方向 | 怎么实现 |
|---|---|
| 思源 → Zotero | 模板里的 `{{zoteroAnnotationLink}}`，形如 `zotero://open/library/items/<附件key>?annotation=<注释key>&page=<页码>`，精确到那一条注释 |
| Zotero → 思源 | 注释旁出现 ↗（**思源自己的图标**），点开跳到思源对应块 |

### 「这条注释发过了」记在哪？

**记在思源那边，Zotero 库里不留任何痕迹。**

之前用 tag（`siyuan:<块ID>`）记过，但那样会污染标签栏、跟着 Zotero 服务器同步、
共享库里的别人也能看见，而且它本身并不是一个链接。

现在的做法是**让思源做唯一真相**：插件写的每个块，正文里带着那条 Zotero 深链，
块的**自定义属性**里还带着注释 key、条目 key、颜色、页码等字段。所以
"这条注释发到了哪个块"可以直接从工作空间里读回来：

```sql
SELECT id, markdown, type, ial FROM blocks
WHERE markdown LIKE '%zotero://open/%/items/%'
   OR ial LIKE '%custom-zotero-annotation-key=%'
```

**按 PDF 增量建索引**：某个 PDF 的侧边栏第一次出现时，只扫这个附件对应的块，把
「注释 key → 思源块 ID」放进内存；发送新注释时立刻更新。

> 以前是启动时全库扫一遍，而 `LIKE '%…%'` 这种前置通配的查询用不上任何索引 ——
> 工作空间一大，每次启动 Zotero 都要等它。现在启动什么都不做，等真的打开一篇论文再说。
> 要全量重建，设置面板里有「重新扫描已发送的注释」按钮。

于是：

- 你的 Zotero 库里**一个标记都不会留下**（没有 tag、没有备注、条目干净）
- 换电脑、重装插件都自动恢复 —— 索引是从思源重建的
- 同一条注释发多次，索引指向**最后一次**的块
- 设置面板里有「重新扫描已发送的注释」按钮，随时可以重建

> 索引认**两条线索**：
>
> - **块的 Markdown** 里的 Zotero 深链。思源会把 `[文字](zotero://…)` 改写成
>   `<span data-href="zotero://…">`，所以要看 `markdown` 列，而不是纯文本的 `content` 列；
> - **块的自定义属性**。它和模板无关：模板里完全不写 `{{zoteroAnnotationLink}}`，
>   历史记录照样能扫回来。
>
> 属性写在**同一次 `block append`** 里（思源的 Markdown 解析器保留块 IAL），
> 所以不会多起一个进程。每条笔记整体包在一个**超级块**（`{{{row … }}}`）里，
> 属性挂在超级块上 —— 也就是索引和「在思源中打开」指向的那个块。
> 一次发送就是一个块：索引、跳转、「替换上次」都以它为单位，不用再猜哪几个块
> 属于这条笔记。

### 每条注释的块属性

| 属性 | 含义 |
|---|---|
| `custom-zotero-annotation-key` | 这条注释的 key（索引的主键） |
| `custom-zotero-item-key` | 文献条目的 key |
| `custom-zotero-attachment-key` | PDF 附件的 key |
| `custom-zotero-color` | 颜色，如 `#ffd400` |
| `custom-zotero-page` | 页码（数字） |
| `custom-zotero-tags` | 注释自己的标签，逗号分隔 |
| `custom-zotero-modified` | 注释在 Zotero 里最后修改的时间 |

在思源里可以直接按这些属性查询、过滤，或者建属性视图：

```sql
SELECT root_id, ial FROM blocks
WHERE ial LIKE '%custom-zotero-color="#ffd400"%'
```

> 属性值里的双引号和反斜杠会被换成空格：思源在 IAL 里不把反斜杠当转义，
> 一个引号会提前结束属性、把后面的内容整段吞掉。注释 key、页码、颜色都不受影响。

> 批量发送时每条笔记各自是一个超级块，属性就挂在各自的容器上，所以分组是精确的
> 一块对一条；旧版笔记没有超级块，仍按末尾不可见的 `zsi=batch` 锚点分组。

### 思源没开的时候

索引在内存里，是从工作空间读出来的 —— 思源没启动，就什么都读不到，侧边栏会把每条注释
都标成「没发过」。所以插件在 **Zotero 偏好 `sentCache`** 里留了一份本地副本
（`注释 key → 块 ID`，按工作空间分开存，最多 2000 条；**不写 Zotero 库**，不违反上面的设计）：

- 启动时先把缓存装进索引，再等第一次真正扫描 —— 思源关着也有 ↗ 标记；
- 扫描完成后缓存被结果**替换**（思源仍然是唯一真相），不是合并；
- 换了工作空间，旧缓存直接忽略，不会把上一个工作空间的标记带过来。

### 思源里的笔记被删了

点 ↗ 之前，插件会先确认那个块还在（先 HTTP、不通再走命令行）。

- **块还在** → 正常打开思源；
- **块没了** → 把 ↗ 标记去掉、从索引里删掉，并弹一个「原笔记已删除，重新发送？」，
  带「重新发送」/「忽略」两个按钮；
- **思源连不上**（既不是「在」也不是「没了」）→ 当作不知道，照旧打开链接，**不会**误删标记。

全量扫描时发现缓存里有、工作空间里已经没有的注释，也会走同一条路：清标记 + 一次性提示
（多条合成一个气泡，不会刷屏）。删除过的 key 会被记住，同一批只问一次。

### 标记立刻出现，不用重开论文

发完之后插件会**直接更新已经渲染好的侧边栏**，↗ 立刻出现在那条注释旁边。
打开一篇论文时，如果这篇的块还没进索引，插件会在后台查一次，查完自动补上标记 ——
不用像以前那样把论文关了再打开。

> 阅读器给插件的挂载点有个奇怪的规矩：**每一次 `append()` 调用都会得到一个独立的盒子**，
> 而**每次重绘都会先把盒子清空**。所以按钮和 ↗ 标记必须放进**同一次** `append()` ——
> 分两次调用就会落进两个盒子，谁也看不见谁，标记就会变成两个。
> 因此查重也是**按注释 key 在整份文档里查**，而不是只看按钮的旁边。
>
> 插件手动插进去的标记会打上 `data-zsi-manual`，阅读器自己渲染的那份没有 ——
> 两条路径不会同时出现在同一个注释上。自检里专门有一步复现这个场景：
> 渲染 → 手动插入 → 再渲染 → 再渲染，标记数量必须始终是 **1**。

### 论文是上次会话留下的？按钮也会补上

Zotero 启动时会恢复上次的阅读器标签页，而**阅读器可能在插件还没加载完时就把侧边栏画好了** ——
这时插件听不到任何渲染事件，侧边栏上一个按钮都不会有。

所以插件启动后会自己看一遍所有打开的阅读器，把缺按钮的补上：注释的 key 能从
阅读器给页码标签起的名字（`page_<注释 key>`）里读出来，补完之后按原样画进阅读器的盒子里。
阅读器下次重绘时会用自己的那份把补的换掉 —— 外观完全一致。

这一遍**不在启动的那一刻**跑（它要 spawn 一次索引查询，不该挡在窗口绘制前面），
而且有三条出口，谁先到走谁：

- **没有打开的阅读器**就根本不启动 —— 之后打开的阅读器都会自己把事件递过来；
- 每个能看见的阅读器都**处理完了**（没有还在加载的）就收工；
- 有阅读器一直没交出侧栏时，45 秒后放弃（间隔从 1 秒退避到 5 秒）。

一个**没有注释**的阅读器不算「还在加载」：它现在没东西可补，以后加了注释会让阅读器
重绘侧栏，而那次重绘插件是能听到的 —— 为它空转纯属浪费。

> 只有**注释预览**里的盒子才算数：工具栏和划词弹窗也有同名的盒子，
> 认错了就会把按钮插到工具栏里去（曾经真的发生过）。

### 点 ↗ 不会再弹确认框

`Zotero.launchURL("siyuan://…")` 会走浏览器的外部协议服务，**每次都要先问一句**
"要打开外部程序吗"。插件改成**直接启动思源**：从注册表（或默认安装位置）找到
Windows 为 `siyuan://` 注册的程序，直接把它跑起来，URL 作为参数传过去 ——
已在运行的思源窗口会被唤到前台并跳到那个块，全程不打扰。

作为双保险，可以把偏好 `silentProtocol` 设成 `1`：插件会把
`network.protocol-handler.warn-external.siyuan` 设为 `false`
（就是那个确认框里"记住我的选择"复选框写的东西），失败的回退路线上也不会再问。

> 这个偏好是**改全局浏览器设置**，所以默认不做，要你显式打开。

> 插件沙箱里读不到注册表服务（`@mozilla.org/windows/registry-service;1` 是
> `undefined`），所以查注册表用的是 `reg.exe` —— 而且 Gecko 的 `Subprocess`
> 只接受**绝对路径**，光写 `reg.exe` 会被判成"不是可执行文件"。

### 思源图标怎么放进去的

**内联 SVG** —— 这是阅读器里唯一可靠的方案。

阅读器的侧边栏跑在**独立的内容进程**里，而插件用 `registerChrome` 注册的 chrome 包是
**local** 的：只有注册者自己的 principal 能加载它。所以 `chrome://zoteroSiYuan/…` 在设置面板里
能显示，在阅读器里却是**一个空方块**（local 包跨进程不可读）。

内联 SVG 不需要任何 URL，因此在任何文档里都能渲染 —— 而 **Zotero 自己的图标本来就是 SVG**。

图形是思源官方应用图标（`resources/stage/icon-large.png`）**逐像素描出来的**：扫描原图的
alpha 与颜色边界，得出四个多边形，配色取自原图的红 `#DA3939` 与深灰 `#3B3E43`：

```js
export const SIYUAN_ICON_SHAPES = [
  { points: "158,84 165,84 165,316 46,435 46,196", fill: "#DA3939" },
  { points: "166,84 173,84 255,166 255,316 166,405", fill: "#3B3E43" },
  { points: "338,84 345,84 345,316 256,405 256,166", fill: "#DA3939" },
  { points: "346,84 465,203 465,435 346,316", fill: "#3B3E43" },

```

还原度做过视觉比对：与官方原图几乎完全一致，14 px 下也能一眼认出。

### 大量注释时的性能

| 做法 | 效果 |
|---|---|
| 索引**整个工作空间一次扫完** | `LIKE '%…%'` 本来就要读整张表，按 PDF 分片不会更快 —— 十篇论文从十次扫描变成一次（5 分钟内的新侧栏直接复用） |
| 多个侧栏同时渲染时**共享同一次扫描** | 恢复八个标签页不会同时起八次全表查询 |
| 侧边栏**事件委托** | 每个 reader 文档一个监听器，而不是每个标记一个 |
| 只在**确实发过**时才建 DOM | 没发过的注释不产生任何额外节点 |
| Fluent 标签**只解析一次** | 几百个注释头不会重复走一遍本地化 |
| 索引刷新**先建后替换** | 查询失败不会把已经知道的映射弄丢 |
| 日记文档 id **每个「笔记本 + 当天」只查一次** | 一次发送只起一个进程（约 0.65 秒，而不是 1.8 秒） |
| 兄弟块列表**只在自检要清理时**才查 | 真实发送少跑一次 `sql` |
| 手动 ↗ 标记按注释**记账**（`WeakMap`） | 渲染几百个注释头时不再每个都扫一遍整个文档 |
| 附件条目与父条目**每批只读一次** | 批量发 50 条少 98 次条目读取 |
| 批量发送**合并成一次写入** | 50 条笔记一次 `block append`，而不是 50 次进程；块与注释靠一条不可见锚点对齐 |
| 同一张框选图**只压缩一次** | 再发一次不再解码 + 重编码整张截图（上限 12 张 / 32 MB，退出即清） |
| 侧栏 watcher **会自己收工** | 没开阅读器就不启动，补完按钮就停，最长 45 秒 |

发送期间**所有**发送按钮都会置灰（不只是被点的那一个）：连点两下不会再写第二条笔记。

## 批量发送

在阅读器里选中多条注释 → 右键 → 「把 N 条注释发送到思源笔记」。

所有笔记先在本地渲染好，再**合并成一次写入**（一条 `block append`，而不是每条起一个进程）。
每条笔记各自包成一个**超级块**，属性挂在容器上，写入完成后按属性把块对回各自的注释，
每组记进索引 —— 所以每一条的 ↗ 标记仍然指向自己的块。
气泡里实时显示「正在发送 3/12…」，全部写完同一个气泡变成结果汇总；
已经发过的（且偏好是「跳过」/「每次问我」）会跳过并在汇总里写「跳过 N 条」。

有失败时汇总气泡会留住，并给两个按钮：**重试失败的那几条**，和**全部重试** ——
后者把这一批整个再发一遍，适合「思源刚启动、第一次几乎全失败」的情况
（已经写进去的会按「已经发过」的偏好跳过，不会重复）。

## 自动发送与待发队列

读论文时不想离开阅读器：设置里的「自动发送与待发队列」打开后，Zotero 里**新建一条注释**，
插件会在它保存好之后（约 1 秒）自动发到思源。

**默认关闭。** 打开后也不是什么都发 —— 只有**同时满足**下面所有条件的注释才会发：

| 条件 | 怎么填 |
|---|---|
| **颜色** | 勾选允许的颜色（黄 / 红 / 绿 / 蓝 / 紫 / 品红 / 橙 / 灰）。一个都不勾 = 不限 |
| **注释标签** | 逗号分隔，匹配注释自己带的标签。留空 = 不限 |
| **注释类型** | 高亮 / 下划线 / 笔记 / 文字 / 框选。一个都不勾 = 不限 |
| **条目分类** | 逗号分隔的 Zotero 类型，例如 `journalArticle,book`。留空 = 不限 |

任何一个维度留空，就是这一项不限；四项全空才会「所有新注释都发」。

思源没启动、或写入失败时，这条注释会进**待发队列**（存在 Zotero 偏好 `pendingQueue` 里，
最多 200 条），不会丢：

- **下次启动** Zotero 时自动重试；
- 之后**任意一次发送成功**，都会立刻触发一轮补发（说明思源回来了）；
- 设置面板里有「立即重试待发队列」和「清空待发队列」，旁边写着还剩多少条。

> 关闭自动发送时队列会**暂停**：已经排队的不再重试，但也不会被删掉，重新打开就继续。
> 面板上的「立即重试」不受开关限制，手动点就会跑。

## 条目列表里直接发送

不用打开 PDF。在 Zotero 的条目列表里右键，插件加了一个「发送到思源笔记」子菜单：

| 菜单项 | 送什么 |
|---|---|
| **发送条目信息** | 作者、年份、出处、DOI 等元数据，整理成一小段 Markdown |
| **发送摘要** | 摘要正文（没有摘要会直接告诉你） |
| **发送笔记** | 这条文献下面的所有子笔记，HTML 转成 Markdown：标题、链接、图片、表格、代码、列表、引用都保留 |
| **发送全部注释** | 这篇文献所有 PDF 上的注释，走的是**批量发送**：每条仍然有自己的块和 ↗ 标记 |
| **同步这篇文献** | 为这篇文献建一篇文档（已存在就复用），把条目信息、摘要、笔记**和注释**写进去；再次同步只更新变了的部分 |

前四项按「发送到」的设置走（今天的日记 / 指定文档 / 每篇文献一个文档）；
最后一项**固定**写进这篇文献自己的文档 —— 它本身就是「每篇文献一个文档」那个目的地的手动入口。
多选条目时，每个条目各执行一次。

「同步这篇文献」把信息、摘要、笔记整体包成一个超级块，块上带 `custom-zsi-section="item"`
和 `custom-zsi-item-key` 两个属性。再次同步时，**这一个块是原地改写的**：块 ID 不变，
所以指向它的链接、反向链接和插件自己的记录都还成立，也不会出现"写了一半、两份都在"的窗口。
万一思源没能原地改写（例如块已经被手动换成别的类型），才退回"先写新块、成功后再删旧块"：

- 你自己在文档里加的标题、正文、想法不会被删 —— 它们没有任何 `custom-zsi-*` 属性；
- 用「发送条目信息 / 摘要 / 笔记」单独写进去的段落会被这次同步**接管**（它们描述的是
  同一篇文献，留着就成了重复内容），之后统一由同步维护；
- 这篇文献的注释笔记不会因此被删 —— 它们带的是 `custom-zotero-annotation-key` 和
  `custom-zsi-section="annotations"`；
- 新内容写失败时旧内容原样保留（先写后删）；
- 旧版写出的三段也带 `custom-zsi-item-key`，升级后第一次同步会照常把它们替换掉。

注释是**增量**同步的：每条注释是单独的一超级块，带注释 key、修改时间和模板指纹。

| 情况 | 做什么 |
|---|---|
| 新注释 | 追加一条，并记进索引，阅读器里的 ↗ 立刻能点 |
| 注释被改过（或模板改过） | 原地改写那一块，块 ID 不变 |
| 注释被删掉 | 只删带 `custom-zsi-section="annotations"` 的块，你自己发进这篇文档的注释不动 |

所以加一条高亮后再同步，代价是一条写入，而不是把整篇文档删掉重写。不需要注释时，
把偏好 `itemSyncAnnotations` 设为 `"0"` 即可，同步就只写信息 / 摘要 / 笔记。

想让每条子笔记**各自成为文献文档下的子文档**，把偏好 `itemNotesAsSubdocs` 设为 `"1"`
（设置面板「发送到」下面的勾选框）。这时同步只把信息 / 摘要写进文献文档，Zotero 里的每条
子笔记各建一篇文档放在它下面：

- 子文档带 `custom-zsi-section="note-document"`、`custom-zsi-item-key` 和
  `custom-zotero-note-key`，所以再次同步会找到同一篇文档、原地改写里面那一个块；
- 子文档的标题取笔记的第一行（和 Zotero 列表里显示的一致）；笔记第一行变了，文档会跟着改名；
- 笔记被删掉后，它对应的子文档也会被移除（进思源回收站，可以找回）；
- 把开关关掉再同步，笔记重新写回文献文档，插件之前建的子文档会被收回。
- 只动带上面两个属性的文档，你自己手工建的同名文档不会被删除或改写。

> 因为「上一次写的内容」是靠思源里的块属性找回来的，不是靠 Zotero 里的状态，所以换电脑、
> 换 Zotero 库、隔了很久再同步，都能找到上一次写的那个块。删掉的部分如果已经手动
> 改过，也会被新内容替换 —— 文档里的事实来源是 Zotero 条目。

子菜单只在选中的是普通条目时出现；右键点在分类、搜索这类没有条目的地方时它自己会藏起来。

## 发送后的反馈

写入成功后右下角会弹一个气泡，写明写进了哪个笔记本，并带一个「在思源中打开」的链接。
气泡**出现在你正在看的那个窗口里**（阅读器就弹在阅读器里，不是弹在背后的条目列表上）。

## 为什么用 siyuan 命令行

插件**优先走思源自带的 `siyuan` 命令行**（SiYuan 3.7+ 内置），命令行不可用时才退回
思源的 HTTP API：

```
# 1. 确保今天的日记存在（已经有了就返回它的文档 ID）
siyuan dailynote create --notebook <笔记本 ID> -w <工作空间>

# 2. 把这条笔记追加进日记，并拿到它写出来的块 ID
siyuan block append --parent <日记文档 ID> --file <临时 md> -w <工作空间> -f json
# → { "id": "20260101000000-abcdefg" }
```

为什么不是一条 `dailynote append`：

- **`dailynote append` 只回答日记文档的 ID，不回答它写了哪个块。** 以前只能拿「创建时间 >=
  发送前那一秒」去 SQL 里捞，同一秒里连发两条就会串位 —— 侧栏回链指到上一条注释的块上。
- **`block append` 直接回答块 ID**，回链和索引都不需要猜。
- 老命令行没有 `block append` 时，插件会自动退回 `dailynote append` + 按时间戳查块，
  功能不丢，只是那条退路上仍然有「同一秒」的歧义。

这样做的好处：

- **不需要 API Token、主机、端口**，思源的日记路径由思源自己按「设置 → 外观 → 日记」解析，
  插件永远和思源自己的设置一致。
- **不受思源 3.8 的「结构化标题模式」影响。** 思源 3.8 起，老的
  `getIDsByHPath` / `createDocWithMd(path)` 接口在开了结构化模式的笔记本里会直接报
  `legacyPathUnsupported`；而 CLI 的日记命令已经把这层兼容处理好了。
- 日记不存在时由 CLI 负责创建（包括 `daily note/2026/10/2026-10-25` 这样的多层路径）。
- **指定文档和「每篇文献一个文档」走同一条写入命令**：`block append --parent <文档 ID>`。
  后者先用 `document create` 建文档，再用 `attr set` 写上 `custom-zotero-item-key`，
  下次直接按这个属性找回文档，不用在 Zotero 里存状态。

> HTTP 兜底有个必须知道的坑：思源内核会**统计失败的鉴权并锁死自己**
> （`认证失败次数过多，请稍后重试`）。所以兜底逻辑优先试你配置里的工作空间、
> 最多只试 3 个 token，绝不横扫你打开过的所有工作空间。

### 为什么这样分

- **`app/` 是行为的拼装，`modules/` 是能力。** `app/` 里的每个文件导出的是一个方法集合，
  `src/index.js` 把它们装进同一个原型 —— Zotero 只认一个 `Zotero.ZoteroSiYuan` 对象，
  但写代码时按功能翻文件。`modules/` 里是纯模块，可以单独 import 进 Node 跑。
- **设置页的 7 个脚本共享同一个作用域。** Zotero 把 `scripts` 里的文件按顺序加载进面板作用域，
  第一个建对象，中间几个用 `Object.assign` 加方法，最后一个 `preferences-boot.js` 才调用 `init()`。
  **顺序变了面板就空**，`npm run check` 会核对这份顺序。
- **一个文件一件事，最多 650 行。** 超过就该拆了；`tools/validate/00-layout.mjs` 每次检查都会
  量一遍，顺便确认每个 `app/` 模块都被装进了原型、每个步骤文件都被调用到 —— 拆完忘记接线是这类
  重构最常见的坑。

## 构建

```bash
npm install
npm run build     # 产物：zotero-siyuan.xpi（构建后自动同步到仓库根目录）
npm start         # 启动 Zotero 并热重载插件（开发用）
npm run check     # 静态回归闸门（496 项）
npm run build:ci  # 同 build，但不动版本号（CI 用）
npm run ci        # build:ci + check
```

`npm start` 需要先在 `.env` 里填好 Zotero 路径；它会建一个独立的 `dev` profile，
不会碰你的主库。

`npm run check` 跑的是 `tools/validate.mjs`，用来挡住**「构建成功但运行不起来」**那一类问题：

- 所有 JS 语法检查；
- **回调是否正确 bind** —— Zotero 派发阅读器事件时用自己的 `this` 调你的 handler，
  不 bind 就会出现 `this._send is not a function`；
- 代码里用到的每个 Fluent id 在两种语言里都有定义；
- **Fluent 文件能被真正的 Fluent 解析器解析**：Fluent 把 `{` 当作占位符的起始，
  所以文本里写了 `{{变量}}` 的那一条会变成 junk，根本到不了界面上 —— 只有解析器看得出来；
- `siyuan` 命令行的候选路径推导（含「只知道 home 目录」这种最差情况）；
- 思源工作空间能被鉴权发现（内核在限流时这一项会被跳过并说明原因）；
- **默认模板能被真的渲染一遍**：callout 在、没有未知变量、回链指向那条注释、
  没有评论时不留空块；
- **模板的条件嵌套不留残渣**：外层条件为空时不会漏出字面量 `{{/if}}`；
- **索引的扫描不会弄丢刚发的注释**：扫描期间发出去的块必须活过那次扫描；
- **自检不接管插件**：它不能替换插件自己的方法，否则你同时点的按钮会被它吞掉；
- **语言包不被钉死在英文**：语言选择跟着 Zotero 的界面语言走；
- 标题里的方括号会被转义，不会把「来源」那行的链接拆坏；
- **框选注释的图片真的能落地**：图片会被复制进工作空间的 `data/assets`、
  Markdown 指向它、没有文字的框选注释照样有摘录块、批量发送时也带着图；
- **图片在发送前会被压缩**：页面截图带着一条全不透明的透明通道，
  压成 JPEG 后通常只剩两成；压完更大就保留原图，压缩坏了也不算错误；
  **压缩程度由用户自己定**（10～100，还能拖滑块）；
- **压缩的规矩有闸门盯着**：压完更大不能用、压缩失败不能抛错、
  关掉压缩就真的不压 —— 这三条都拆开验过，**去掉修复就会 FAIL**；
- **模板没写图片变量时，图片也会进笔记**（自动追加），写了就只出现**一次**；
- **没有值的变量不占位置**：一行里只有变量而它们都没有值时，整行消失；
  空的引用块也不是一个孤零零的 `>`；
- **只用真实存在的文件 API**：`IOUtils.newFile` 根本不是 Gecko 的 API
  （`IOUtils.write` 直接收路径），`PathUtils.join` 也不接受**带分隔符**的组件 ——
  这两个都真的发生过，所以闸门里的替身**不**比真的更宽容；
- **模板编辑**：整块变量会自动独占一行并保留缩进、未知变量和没闭合的条件会被找出来；
- **条件可以可视化插入**：选中的文字会被包进 `{{#if 变量}}…{{/if}}`，标签各占一行、
  内容原样保留；按按钮时选区不会丢；
- **条件有另一分支**：`{{else}}` 归它所在的那一层条件，没被走的那一支连行一起消失；
  落单的 `{{else}}` 会被校验找出来；
- **没人引用的图片会被收走**：写失败的发送会把自己那张图删掉，
  自检也会把它写进去的图片收回来 —— 工作区是用户的，不留垃圾；
  自检还会**前后对比**工作区的图片目录：写了一半失败而没被 Markdown 提到的图也会收走，
  而**任何笔记引用着的图都会留下**（哪怕是你在自检运行时自己发的那条）。
- 打好的 XPI 里该有的文件都在、manifest 字段齐全、**manifest 的版本号与 `package.json` 一致**、
  `prefs.js` 只含双引号格式的 `pref(...)` 行。

> **为什么版本号必须每次都动**：Firefox 把已安装插件的清单缓存在 profile 的
> `extensions.json` 里，**同版本号替换 `.xpi` 可能不生效**，旧代码会继续跑。
> 所以每次改代码都要动 `addon/manifest.json` 的版本号 —— `npm run build` 会自动
> bump，`npm run check` 会盯着 manifest 与 `package.json` 是否一致。

> **装插件的正确顺序**：**先关掉 Zotero，再覆盖 `.xpi`**。Firefox 用内存映射
> （memory-mapped section）打开着 XPI，Zotero 运行时覆盖它会直接失败
> （`请求的操作无法在使用用户映射区域打开的文件上执行`）。覆盖失败如果被忽略，
> Zotero 重启后就会加载旧代码 —— 而且日志里看不出来。装完记得比一下哈希。
>
> ```powershell
> # 关 Zotero → 确认进程没了 → 覆盖 → 校验哈希 → 再启动
> [System.IO.File]::Copy(".\zotero-siyuan.xpi", "$profile\extensions\zotero-siyuan@example.com.xpi", $true)
> (Get-FileHash "$profile\extensions\zotero-siyuan@example.com.xpi").Hash -eq (Get-FileHash ".\zotero-siyuan.xpi").Hash
> ```
>
> **覆盖之后要重启两次才保险** —— 这一点是实测出来的，不是听说：
> 换了 XPI 之后**第一次**启动 Zotero，跑的**还是旧代码**（自检报告里能看出来：
> 它报告的字段是旧版的样子）；第二次启动才加载新代码。
> 所以装完插件后**再重启一次 Zotero**，再去验证行为。
> 怎么知道跑的是新代码？看自检报告里有没有新加的字段 ——
> 比如图片压缩会多出 `compressed` / `originalSize` / `sentSize`。

## CI 与发布

`.github/workflows/` 下有两条流水线，**都不需要你本机有思源**：

| 流水线 | 什么时候跑 | 做什么 |
|---|---|---|
| `ci.yml` | 推 `main`、提 PR、手动触发 | Ubuntu + Windows 各跑一遍：装依赖 → 构建 → 静态闸门 → 把 XPI 存成产物 |
| `release.yml` | **网页上点一下**（或推 `v*` 标签） | 改版本号 → 提交 → 打标签 → 构建 → 核对 → 生成 `update.json` → 发 Release |

**CI 的构建不动版本号。** 本地 `npm run build` 每构建一次都会把版本号 +1
（Firefox 认缓存，同版本号换 XPI 可能不生效）；CI 用的是 `npm run build:ci`
（`tools/bump-version.mjs --no-bump`），它**验证已提交的源码**，所以工作区必须
保持干净 —— 流水线里那句 `git diff --exit-code` 就是守这个的。

**CI 上没有思源，所以有两项检查会跳过而不是失败**：命令行候选路径的实测、
以及「工作空间能被鉴权发现」。它们要的是一台真的装了思源的机器；
在没有思源的机器上，它们的结论只能是「没法判断」，而不是「插件坏了」。

### 发版：在网页上点一下

**不用敲任何命令。** 打开仓库 → **Actions** → 左边选 **Release** →
右上角 **Run workflow** → 选分支（`main`）→ 选版本号往哪走 → 按绿色的
**Run workflow**。

```
Run workflow
  ├─ bump:   patch / minor / major     ← 这次版本号往哪走
  └─ draft:  ✓ / ✗                     ← 先发草稿看看
```

然后等它跑完（**约 1 分钟**），结束时会看到：

```
✓ Move the version
✓ Commit the version
✓ Tag the release
✓ Build the XPI
✓ The tag must be the version of the sources
✓ Write the update manifest
✓ Publish the release
```

它替你做完的事：

- **改版本号** —— `patch` 加一（`0.2.96` → `0.2.97`）、`minor` 进一（→ `0.3.0`）、
  `major` 进一（→ `1.0.0`）。四处一起改：`addon/manifest.json`、
  `package.json`、`package-lock.json`、`src/version.js`；
- **提交并推上 `main`** —— 所以 `main` 永远是发出去的��份代码；
- **打标签 `v0.2.97` 并推上去**；
- **构建 XPI**，用 `tools/check-release-version.mjs` 核对
  **标签 = 版本号**，对不上就**拒绝发布** —— 否则会发出一个「自称是别的版本」
  的 XPI，而插件自己永远更新不到它；
- **写出 `update.json`**（含 XPI 的 sha512），连带 XPI 一起挂到 Release 上。

结束后：

- 仓库右侧的 **Releases** 页会多出一条 `v0.2.97`，挂着 `zotero-siyuan.xpi`
  和 `update.json`；
- **Zotero 里的插件自己就能找到新版本**（设置 → 插件 → 齿轮 → 检查更新）。

> **先发草稿**：勾上 `draft`，Release 会停在草稿状态，你可以在 Releases 页
> 点一下「Publish release」才真正放出去。适合想先下载 XPI 试一下的情况。

> **版本号在四个地方**：`addon/manifest.json`、`package.json`、
> `package-lock.json`、`src/version.js`。`npm run check` 盯着这四处一致 ——
> `package-lock.json` 曾经掉队（它还停在 `0.2.54`，而别处已经是 `0.2.95`），
> 而 `npm ci` 会拿它和 `package.json` 比对，**版本对不上时安装直接失败**。
> 现在 bump 脚本会一起改它，闸门也会查它。

### 发版：命令行那条路（可选）

如果你更习惯用 git：

```bash
npm run build       # 版本号 +1，四处一起改
npm run ci          # 本地验一遍
git add -A && git commit -m "chore(release): v0.2.96"
git push origin main
git tag v0.2.96 && git push origin v0.2.96
```

推上标签会触发 `release.yml`（`push: tags` 那条入口），它会跳过「改版本号、
提交、打标签」这三步，只做构建、核对、生成 `update.json`、发 Release。

> **标签必须等于版本号。** `tools/check-release-version.mjs` 会核对
> `v0.2.96` == `package.json` 里的 `0.2.96`，对不上就**拒绝发布**。
> 标签打错了就把它删掉重打：
> `git tag -d v0.2.96 && git push origin --delete v0.2.96`。

### 日常改动：还是两条命令

```bash
# 1. 改代码，然后本地先跑一遍 CI 跑的那两步（和流水线里一模一样）
npm run ci          # = build:ci + check，产物是 zotero-siyuan.xpi

# 2. 提交、推送
git add -A && git commit -m "feat: …"
git push origin main
```

推上去以后：

- **打开仓库的 Actions 页**（`https://github.com/loonghfut/zotero-siyuan/actions`），
  最新的那次 CI 在最上面。点进去能看到 Ubuntu 和 Windows 两列各自的日志。
- **绿勾 = 通过**。红叉就点进去看是哪一步：`Run the static checks` 失败时，
  日志里会有一行 `[FAIL] <检查名> — <原因>`，把它抄到本地跑 `npm run check` 就能复现。
- **想手动跑一次**：Actions 页右上角 `Run workflow` → 选分支 → `Run workflow`。
- **拿构建好的 XPI**：CI 跑完的那次运行底部有 `Artifacts`，下载
  `zotero-siyuan-windows-latest` 之类的压缩包，里面就是 `zotero-siyuan.xpi`。
  想直接拿文件，也可以用 Release 里的那个（见上）。

> **CI 失败时先看 `Run the static checks`**，不是看 `Build the XPI` ——
> 构建这一步在本地也是同一条命令，出问题的话本地早就发现了。
> 只有「The build left the sources alone」这一步是 CI 独有的：
> 它说明构建**改了受版本控制的文件**，通常是版本号被动了。

## 端到端自检

插件**自己就是自己的测试台**：在设置页点一次「运行端到端自检」，它会把结果写成 JSON 报告：

```
%LOCALAPPDATA%\Temp\Zotero\zotero-siyuan-selftest.json
```

> 自检**默认不在启动时跑**。它要在后台轮询十几秒，以前还会在真实阅读器里点一次真实按钮 ——
> 用户看到的是一个假的「已发送到思源笔记」气泡。现在只有设置页的按钮才会启动它。

自检走的是**和你点按钮完全一样的代码路径**，一个环节都不 mock：

```
renderSidebarAnnotationHeader 事件 → 真的按钮 → 真的 click()
  → _send() → 已发送检查 → 选模板 → 收集变量 → 解析目标位置 → 渲染 → 写思源 → 拿到块 ID → 写进索引
```

默认是 **dry run**：最后一步换成 `siyuan dailynote append --dry-run`，让思源自己校验
这条命令，但**不写任何东西**。

把偏好 `extensions.zotero.zoteroSiYuan.selfTestWrite` 设成 `1`（在 `about:config` 里，
布尔值 `true` 也认），自检就会**真写一次**：它会挑你库里一条真实的注释，发送、核对块 ID
记进了索引，然后**把自己留下的痕迹全部清掉**（删思源里的块）。

> 自检**只删自己写的那几个块**。`block append` 会回答它写的第一个块，同一个 `created`
> 秒内的顶层块都是这一次发送写出来的 —— 它们全部会被删掉，而不会碰到你自己早先发的那一条。
> 清理之后，索引会指回你原来那个块。

自检里还有两步是拿**真的阅读器**跑的：一步检查每个打开的阅读器都显示出了按钮
（包括插件启动前就画好侧边栏的那种），一步在真的侧边栏里点一次按钮，确认
**每条注释恰好一个 ↗**。这两步只在设置页点按钮时运行（启动时的自检不碰阅读器），
跑不动的时候（比如阅读器还没加载 PDF）会跳过并写明原因，不会误报失败。

> 自检里那一次点击不会弹「已发送」气泡，也不会把按钮改成「已发送」：
> 那不是你的发送，就不该有你的反馈。

失败时还会额外写一份 `zotero-siyuan-diagnostics.json`，里面有每个候选路径为什么不行、
`Services.dirsvc` / `PathUtils` / `Services.env` 在插件作用域里到底能不能用等原始信息。

清理自检留下的块：

```bash
node tools/siyuan-cleanup.mjs --workspace "D:\SiYuan\workspace" --list
node tools/siyuan-cleanup.mjs --workspace "D:\SiYuan\workspace" --marker ZoteroSiYuanSelfTest
```

> 工作空间可以省略：`--workspace` 不给时，脚本先看环境变量 `SIYUAN_WORKSPACE`，
> 再问思源自己（`siyuan workspace info` 回答当前打开的是哪个工作空间）。
> 脚本里**没有写死任何路径** —— 写死的路径只在一台机器上是对的，
> 而错了以后要等到"找不到今天的日记"才看得出来。

## 安装

### 方式一：安装 XPI

「工具 → 附加组件 → 齿轮 → 从文件安装附加组件」，选 `zotero-siyuan.xpi`。

### 方式二：从源码加载（开发用）

1. 启动一次 Zotero，用独立 profile：`zotero.exe -p dev`
2. 关闭 Zotero。
3. 在 profile 的 `extensions` 目录里建一个**以插件 ID 命名**的文件
   （`zotero-siyuan@example.com`），内容是插件源码目录的**绝对路径**，不含任何其它字符。
4. 编辑同目录下的 `prefs.js`，删掉含 `extensions.lastAppBuildId` 和
   `extensions.lastAppVersion` 的两行，保存。
5. 启动 Zotero，插件就会出现在「工具 → 附加组件」里。

> `prefs.js` 的格式有坑：它会被解析两次 —— Zotero 启动时用 JS 加载（单双引号都行），但
> Firefox 安装 XPI 时用一个只认 `pref("name", value);`（**双引号**）的严格解析器。
> 本项目用 scaffold 生成 `prefs.js`，格式天然正确。

## 设置

插件设置面板（Zotero 设置里插件名下面那一项）：

| 偏好 | 默认 | 说明 |
|---|---|---|
| `cliPath` | 空 | `siyuan` 命令行路径。留空则自动查找 |
| `workspace` | 空 | 思源工作空间目录。留空 = 用 `siyuan` 当前的工作空间 |
| `notebook` | 空 | 写进哪个笔记本：面板里是**下拉框**，打开设置时自动列出来；留空 = 第一个可用的笔记本 |
| `destination` | `daily` | 发送到：`daily` 今天的日记 / `document` 指定文档 / `item` 每篇文献一个文档 |
| `targetDocument` | 空 | 「指定文档」的标题或块 ID |
| `itemDocName` | `{{title}}` | 「每篇文献一个文档」的新文档标题（可用模板变量） |
| `itemDocPath` | `/` | 新文档放在哪个路径下 |
| `itemNotesAsSubdocs` | `0` | 是否把每条子笔记单独建成文献文档下的子文档。`1` 打开；关闭后再同步会收回子文档 |
| `sentAction` | `ask` | 已经发过的注释：`ask` 每次问 / `skip` 跳过 / `send` 再发一条 / `replace` 替换上次 |
| `template` | 空 | 发送模板。留空 = 内置默认模板 |
| `itemTemplate` | 空 | 「每篇文献一个文档」单独用的模板。留空 = 沿用 `template` |
| `templates` | `[]` | 你自己保存的模板（JSON 数组：`id` / `name` / `template`）。留空 = 一份都没存 |
| `autoSend` | `0` | 新建注释时自动发送。**默认关闭** |
| `autoSendColors` | 空 | 自动发送的颜色过滤（逗号分隔的十六进制色值） |
| `autoSendTags` | 空 | 自动发送的标签过滤（逗号分隔） |
| `autoSendTypes` | 空 | 自动发送的注释类型过滤（`highlight,note,image` 等） |
| `autoSendItemTypes` | 空 | 自动发送的条目分类过滤（`journalArticle,book` 等） |
| `pendingQueue` | `[]` | 待发队列（JSON 数组：`key` / `attempts` / `at`），最多 200 条 |
| `sentCache` | `{}` | ↗ 标记的本地副本（`注释 key → 块 ID`，按工作空间分开，最多 2000 条） |
| `imageCompress` | `1` | 图片发送前压缩（框选截图、子笔记里的图片） |
| `imageQuality` | `82` | JPEG 质量（10～100） |
| `selfTest` | `0` | 启动时跑一次端到端自检（dry run）。默认关闭 |
| `selfTestWrite` | 空 | 设成 `1` 时自检会真的写一条（写完自己清理） |
| `silentProtocol` | 空 | 设成 `1` 才把 `network.protocol-handler.warn-external.siyuan` 置为 `false`（改的是全局浏览器偏好） |

面板里的「测试连接」会跑一次 `siyuan workspace info` + `siyuan notebook list`，
把找到的笔记本列出来，并显示**实际使用的**可执行文件路径和工作空间。
笔记本下拉框在**打开设置面板时**就会去列一次；测试连接成功后会再刷新一次。
思源没开时下拉框只保留你之前选的那个，并在后面标注「在思源里没找到」——
不会因为列不出来就把设置清空。

命令行不可用时它会自动探测思源的 HTTP API：**两个通道任一可用就算连通**。
只有 HTTP 走得通的时候，结果里会明确标注「通过思源 HTTP 接口连接（命令行不可用）」——
发送照样能用，只是**重扫历史记录在建 index 时会慢一些**（走的是 HTTP 查询而不是本地 SQL）。

> **路径分隔符的坑**：Firefox 启动外部程序前会检查
> `PathUtils.isAbsolute(path)`，而 Gecko 在 Windows 上不认正斜杠路径 ——
> `C:/Users/.../siyuan.exe` 会被判为「不是可执行文件」，`C:\Users\...\siyuan.exe` 才认。
> 插件会把正斜杠换成反斜杠，并且**先验证再使用**；你填的路径不可用时会
> 自动回退到自动查找，并在日志里说明。留空即可全自动。

查你自己的工作空间和笔记本：

```powershell
siyuan workspace list
siyuan workspace info
siyuan notebook list -w "D:\SiYuan\workspace"
```

## 已知限制

- 阅读器界面用**自己的 Fluent bundle**，不读插件的 `.ftl`，所以按钮的提示文字由插件在插件
  作用域里解析后以普通属性写入。插件按 Zotero 的界面语言挑选语言包（`zh-CN` → `en-US`），
  某个词条在译文里缺失时退回英文，不会整条消失。
- 注释面板的按钮由 `Zotero.Reader` 的 `renderSidebarAnnotationHeader` 事件注入。
  这是 Zotero 官方的阅读器扩展点，但 Zotero 每次升级都可能调整阅读器内部结构。
- 有几处只能依赖 Zotero 的**私有成员**：`Zotero.Reader._readers`、`reader._iframeWindow`、
  `ZoteroPane.document`。每一处都有 `try/catch` 兜底（拿不到就跳过，不会让发送失败）。但
  Zotero 换大版本时，这几处是最该回归的地方：先在阅读器里点一次按钮，再看侧栏有没有出现 ↗。
- 自检**默认不在启动时跑**。需要时在设置页点「运行端到端自检」；想让它每次启动都跑，
  把 `extensions.zotero.zoteroSiYuan.selfTest` 设为 `1`（启动时那一趟不会碰阅读器）。
- 自检在跑的时候**不会碰你的发送**：它只是在按钮被点中的那一瞬间挂上观察钩子，
  钩子只作用于它自己点的那一次。你在这期间自己点的按钮，写的还是你自己的日记。
- **自动发送只作用于「打开开关之后新建的注释」**，不会回头补发历史注释；
  待发队列也只保留 key，重试时会重新渲染——所以一条注释在排队期间被改过，发出去的是改后的样子。
- 条目级发送（右键菜单）按目的地设置写入，**不参与「已经发过」的检查**，
  也不在注释索引里留记录；它送的是整条文献，不是某一条注释。
- 自检结束时会删掉它自己写的那几个块。如果它无法确认某个块是自己写的（比如走的
  是 HTTP 接口，内核只回答第一个块 id），它就**只删那一个确定的**，其余一律留下 ——
  宁可在日记里多留一段，也不删你自己的笔记。
- 写入结果「不知道有没有成功」时（命令超时、输出读不出来），插件**不会重试，也不会
  删掉那张图**。此时弹窗会留在屏幕上不动，提示你先看一眼今天的日记再决定要不要重发。
  因为这种情况下重试很可能写出两条。
